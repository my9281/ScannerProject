# 维修过程、扫码收货与 Web 看板需求草案

更新：2026-11-14  
状态：总体需求仍待逐步规划；本轮仅实施 Camara.WPF 的“开始维修”SN/SKU 录入，复用既有专用表和接口。运单收货、通用维修过程及 Web 看板继续待规划；不代表已部署。

## 1. 目标与本次范围

搭建一个相对通用的业务记录系统，先覆盖维修过程和扫码收货，再由 Web 看板展示这些记录。

原阶段仅整理需求；用户随后确认本轮仅做 Camara.WPF 的“开始维修”录入，详见 [录入说明](camara-repair-start.md)。本轮不做运单收货、通用维修过程或看板，不执行线上数据库变更和部署。

## 2. 已明确的需求

| 模块 | 需求 | 当前明确程度 |
| --- | --- | --- |
| 通用记录系统 | 能持续记录维修过程，不能只支持一次“开始维修”扫描 | 已明确方向，过程事件范围待定 |
| 维修操作入口 | “开始维修”SN/SKU 录入已在 Camara.WPF 实施；其他维修过程记录入口仍待规划 | 本轮仅落实开始维修录入 |
| 扫码收货 / 入库扫描记录 | 在 Camara.WPF（仓库项目 `WPF.Camara`）扫描一个运单号，记录并确认收货 | 已明确功能与客户端归属 |
| 承运商 | 运单可能来自 USPS、FedEx | 已明确至少覆盖这两类；是否扩展其他承运商待定 |
| Web 看板 | 展示维修过程记录和收货内容 | 已明确，布局与指标待定 |

### 2.1 维修过程记录

需要从“扫描一次即记为开始维修”的单点功能，扩展到可描述维修经过的记录能力。

原始扫描要求保留为设计输入：

- 一次录入包含 SN 和 SKU，两项均允许清除。
- 同一次上传前必须两项齐全，每项长度不超过 50 位。
- 记录扫描第一个编码的时间。
- 记录“开始维修”这一业务动作。

上述规则最终由哪个客户端执行、是否用于所有维修事件，以及首扫时间是否等同于维修开始时间，需结合 WPF 工作流程重新确认。

维修过程的候选事件可包括：开始维修、维修备注、等待配件、维修完成等。这些仅用于后续讨论，暂不列为全部必做功能，也不预先确定状态流转规则。

### 2.2 扫码收货

- 扫描对象为运单号，以此形成收货确认记录。
- 至少考虑 USPS 和 FedEx 的运单。
- 收货与维修是不同业务动作，扫描运单不能直接视为开始维修。
- 入库扫描记录确定放在 Camara.WPF，对应仓库项目 `WPF.Camara/WPF.Camara.csproj`。本阶段规划不增加 PDA 收货入口。
- 暂不把承运商物流查询、签收证明或与订单自动匹配列为已确认需求。

此处“入库扫描记录”指上述运单扫码收货记录；是否进一步联动库存入账、库位或设备明细，尚未确定。客户端归属已确定，具体页面、保存方式和上传流程后续规划。

“确认收货”目前指本系统记录了现场收货动作；是否需要核对实物数量、订单或包裹内容后才算完成，留待确定。

### 2.3 Web 看板

Web 端需要能够查看上述两类业务内容。候选展示方式如下，具体范围待定：

| 内容 | 候选展示 |
| --- | --- |
| 维修记录 | SN、SKU、业务动作、发生时间、维修过程明细 |
| 收货记录 | 运单号、承运商、收货确认时间 |
| 记录检索 | 按编码、日期、业务类型筛选 |
| 业务关联 | 条件具备时，从运单查看相关设备，或从设备查看维修经过 |

数量统计、待处理提醒、自动刷新、导出、异常处理、编辑权限等，均待后续确定，暂不承诺实现。

## 3. 与上一版扫描记录实现的关系

上一版代码围绕 PDA 的 SN/SKU 配对上传设计，使用独立表 `repair_scan_records`，固定写入“开始维修”，并提供 `/api/repair-scans`。相关说明见 [原扫描记录说明](../Scanner.Web/Database/repair_scans.md)。

本轮需求扩大了记录范围，并重新考虑操作入口，因此不能直接把上一版的专用表或 PDA 页面认定为最终通用方案。

- 本轮复用上一版专用表和接口，补充 Camara.WPF 开始维修录入；通用记录系统仍需先明确业务对象和记录方式。
- 本次不删除、不回退上一版代码，也不执行其建表脚本。
- 若后续已有实际数据，需要评估兼容或迁移；若尚未使用，可在正式实施前调整方案。当前部署与数据状态需要另行核实。

## 4. 设计建议：先区分业务对象，再确定表结构

以下为规划建议，尚未确定为实现方案。

### 4.1 业务对象

| 对象 | 主要标识 | 需要解决的问题 |
| --- | --- | --- |
| 包裹 / 收货 | 运单号、承运商 | 哪个包裹何时被确认收到 |
| 设备 | SN、SKU | 维修针对哪台设备、哪个型号 |
| 维修单或维修轮次 | 待定义的业务编号 | 同一 SN 多次返修如何区分 |
| 过程记录 | 独立记录编号 | 在某个业务对象上，何时发生了什么动作 |

建议不要先假定一个运单只对应一个 SN；包裹与设备之间的对应关系，应在实际收货流程确认后再设计。

### 4.2 记录的共性

建议评估以下共同字段：记录编号、业务类型、关联对象、动作、实际发生时间、服务器接收时间、操作人、来源客户端、备注。

把“动作历史”和“当前状态”分开考虑：历史用于查看经过，当前状态用于看板筛选。是否采用统一事件表、各业务独立表加共用字段，或其他结构，后续再决定。“通用”不预设为所有数据必须塞进同一张表。

时间建议区分首扫时间、操作确认时间与服务器接收时间。是否用于计算维修耗时，必须先确定业务口径。

### 4.3 数据可靠性

后续设计需明确：

- 网络失败后的本地保留与重试，避免同一次操作重复写入。
- 重复扫描同一个运单与重复提交同一请求的区别：前者可能是业务重复，后者应避免产生重复记录。
- 误扫、错配 SN/SKU、误确认收货后的更正方式，以及是否保留原记录。
- 编码保留前导零，不按数字存储；运单长度和条码格式需按实际扫描内容另定，不能直接套用 SN/SKU 的 50 位规则。

## 5. 后续需要逐步确定的问题

| 优先顺序 | 问题 | 影响 |
| --- | --- | --- |
| 1 | 现场从收货到开始维修，实际有哪些步骤、由谁操作？ | 决定记录边界和操作入口 |
| 2 | 维修记录以设备为主，还是以维修单 / 维修轮次为主？ | 决定多次返修与历史查询方式 |
| 3 | “开始维修”何时成立：首扫、两码齐全，还是操作人点击确认？ | 决定时间与状态口径 |
| 4 | 维修过程由哪个 WPF 项目负责、PDA 是否仍参与？已确定的 WPF.Camara 收货入口如何组织页面？ | 细化客户端职责及页面流程 |
| 5 | 同一运单再次扫描如何处理？一个包裹是否允许多个设备？ | 决定去重和关联关系 |
| 6 | 运单是否自动识别承运商？识别不出时是否允许手动选择？ | 决定扫码校验与异常处理 |
| 7 | 操作人如何识别，谁能更正记录？ | 决定权限和追溯能力 |
| 8 | 看板优先解决“查经过”“看当前进度”还是“每日数量”？ | 决定首版展示范围 |

## 6. 建议推进顺序

1. **梳理实际流程**：用一台设备、一个包裹的完整实例，确定收货和维修各自的起止点及责任人。
2. **定义记录口径**：确定对象、事件、时间、重复与更正规则，明确 WPF / PDA / Web 的分工。
3. **设计最小数据模型和接口**：评估上一版代码的复用与迁移，不提前锁定表结构。
4. **分批实施**：分别完成维修记录、扫码收货与 Web 查询展示；先做哪项由现场优先级决定。
5. **再扩展看板与统计**：在记录口径稳定后增加进度、数量和耗时指标。

## 7. 后续验收场景草案

这些用于后续规划测试，并不表示本次开始开发：

- 维修：SN/SKU 缺一不可上传，超过 50 位不提交，清除与重扫时的计时规则符合最终约定。
- 过程：能按同一维修对象查看多条动作历史；同一 SN 再次返修时可区分不同维修过程。
- 收货：USPS 和 FedEx 的实际运单均可按约定扫描，能确认收到并检索记录。
- 重复与更正：网络重试不新增重复记录，重复收货和误扫可按约定处理。
- 看板：能查到收货与维修内容，时间、状态和明细与操作记录一致。
