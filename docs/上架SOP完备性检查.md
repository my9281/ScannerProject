## 结论

**尚未完备。** 已记录“找到设备 → 检测或箱材翻新 → 标签 → 打托扫码 → 导入与打印 → 签字缠膜 → 送达上架区域待确认”，可以作为这一段作业的参考。缺少“谁确认 → 何时上传 → 实际落位 → 谁交接 → 如何核对系统成功”的闭环，不能仅凭送达待确认区认定上架完成。

## 代码已能确认的行为

以下是实现事实，用于补写操作说明；不替代现场负责人确认作业顺序。

1. **基础表和扫码批次是两种数据。** WPF 共享缓存提供基础资料；“选择 TXT”加载当前托盘扫码文本。“下载批次”选择 PDA 上传的 SKU/SN 批次，替换当前明细后按基础表匹配，不用于刷新基础表。两种扫码来源应选定同一托盘数据，不能误将另一批次覆盖进来。
2. **按钮可用不代表匹配全部通过。** 控制器在有明细时启用上传，未以“未匹配为 0”作为统一拦截条件。文档必须明确未匹配、SKU/SN 不一致由谁处理、什么条件可继续，不能依赖按钮状态代替核对。
3. **上传会实际改变业务状态。** WPF 的上传调用 `POST /api/shelved-pallets`。服务端事务写入上架明细、设置设备已上架、将对应周期未审核工单置审核位并递增版本、按 SN 归档良品区记录。因此上传不能当作“只预存数据”；工单可能随即从平板待处理列表中消失。
4. **成功需要有效回执。** 客户端校验请求 ID、明细数量和 UUID 数量。上传后应核对提示中的托盘号、数量和时间，并按服务端记录查询复核。飞书通知或纸质打印不能单独证明整个实物交接完成。
5. **失败可能需要原请求重试。** 客户端为待确认的相同上传内容保存请求标识；服务端支持同标识同内容重放。超时或回执异常不证明数据库一定未提交，应保留原内容并查询/重试，不能随意改数据发起另一批。成功确认后本地待请求记录清除，不能把再次点击成功上传视为一定会被同请求去重。
6. **上架时间来自服务端。** 当前服务使用服务器本地时间生成上架时间，不是纸上签字日期。跨日、补录及服务器时区对应哪一天，需要部署核对及业务约定。

| 优先级 | 问题 | 需要形成的明确记录 |

| 阻碍闭环 | 谁接收和确认整托，差异由谁处理？ | 操作人/复核人/接收人职责；核对 SN、SKU、件数、托盘、标签、成色和禁售；确认记录及差异处理路径 |

| 阻碍闭环 | 托盘号是否等于库位，如何防重复？ | 分别定义托盘与库位、分配规则、使用范围、复用条件；不可凭示例均为 8 就视为同一字段 |

| 阻碍闭环 | 两份清单最终由谁留存？ | 随托份与交接份的去向、签字角色、保存位置、电子资料关联方式及期限 |
| 补齐分支 | 禁售、非 OK、有维修或换配件设备如何处理？ | 判定标准、处理入口、复核与放行条件、标签要求；成色判定标准 |
| 补齐分支 | 翻新完成后如何打印？ | 实际页面入口、SKU 转换及双二维码核对截图；与第 5 节贴标规则衔接 |
| 补齐异常 | 未匹配、基础表过期或换托怎么办？ | 数据来源/日期、更新责任人；更换实物后重新扫码、重印和作废旧纸的操作要求 |
| 补齐异常 | 非 11–29 件及超重如何处理？ | 托盘、机型重量与堆叠限制、混托条件及特殊批准责任人 |
| 补齐异常 | 跨日补录、打印失败或移动后破损怎么办？ | 日期规则、重打核对及旧单处置、重新整理与复核责任 |

## 闭环验收清单（补写后现场验证）

- [ ] 正常 OK、只换箱、实际维修、禁售设备均有可执行分支，不靠截图示例推断。
- [ ] 一托货能从 SN 核对一直执行到真实落位、系统成功及接收人签字，各步骤明确责任人。
- [ ] 实物、扫码文件或批次、WPF 明细、两份清单、汇总标签和服务端记录的 SN/SKU/件数一致，托盘与库位可追溯。
