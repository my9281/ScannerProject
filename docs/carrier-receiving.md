# 仓库收货监控方案：两池、PDA 实收与每日看板

更新日期：2026-11-15。状态：目标方案，部分代码已实现，尚未完整交付或部署；当前进度见文末。

核心原则是人总会犯错，因此由系统呈现操作要求、逐项确认并保存记录，减少依赖个人记忆。

| 优先级 | 范围 | 安排 |
| --- | --- | --- |
| P0 | PDA扫描收货、收货时间和可靠上传 | 计划11月17日实装；不以两池和完整看板交付为前提 |
| P1 | 同步客户预报池与承运商记录池，匹配并形成Web收货看板 | 展示包裹实收、待收、差异与数据时效 |
| P2 | 基于已有开始维修入口建设型号checklist、JSON配件表、装箱逐项点选和维修记录 | 蓝牙检测及配件核对计划11月底前逐步实装 |
| P3 | 类似Teams任务分配方式，按角色和具体人员展示每日任务与未完成项 | 后续规划，未约定上线日期；不是要求接入Teams接口 |

解绑归入P3每日任务管理，不作为近期独立软件模块。例如周一经理看到“完成入库检测”，技术经理看到“完成解绑”“完成报废审核”；具体角色、日期和任务规则后续确认，不写死。

P1看板以包裹对账为中心，P3 Dashboard以个人任务为中心，二者分别建设。现有配件Excel已转JSON，后续重点是资源接入、型号映射和操作页面，不重复安排转换工作。

## 一、目标与业务结构

仓库接收 BLUETTI 等客户的 FedEx、USPS 来件。司机不知道准确件数，现场通常整板、整批签收，无法靠交接签字判断每个包裹是否到仓。

系统采用“两池 + 一份实收记录 + 一个看板”，持续回答：客户要求收什么、承运商记录是什么、仓库实际收到什么、今天还差什么。

| 组成 | 职责 | 数据来源 |
| --- | --- | --- |
| 客户需求/预报池 | 明确需要收货的工单与包裹 | 定时从 BLUETTI 等客户系统拉取预报工单、RMA 与 FedEx/USPS 运单 |
| 承运商记录池 | 保存运输、派送和送达事实 | FedEx、USPS 获授权的记录接口或事件推送，能力待验证 |
| PDA 实收记录 | 记录仓库实际逐件收货 | PDA 扫描运单并上传 Web |
| 每日收货看板 | 对账、展示今日进度与异常 | 持续匹配两个池与 PDA 实收记录 |

这里的数据池是包裹信息集合，不是商品可用库存。外箱扫描不等于箱内商品已拆包验货或正式入库；客户预报和承运商显示送达都不能替代仓库实收。

## 二、客户需求/预报池

Web 后台定时拉取客户预报工单，BLUETTI 为首个接入对象，后续支持其他客户。手工录入只作补录，不能代替客户系统定时同步这一主流程。

保存客户、来源系统、来源工单 ID、RMA、目标仓库、来源状态、来源更新时间、最后同步时间，并关联承运商、运单号与来源提供的预计到货日期。型号、SN、数量等字段按实际来源保留，缺失时不虚构。

同步规则：

- 首次按配置范围回溯未完成工单，之后按更新时间或来源游标增量拉取，并做重叠回查处理迟到更新。
- 分页读取，数据成功落库后才推进对应游标；失败重试不重复生成工单或包裹。
- 一张工单可关联多个包裹，一个包裹也可能关联多个工单；工单数、包裹数和商品数量分开统计。
- 运单缺失、承运商不明、仓库不匹配的记录进入待补资料列表，不自动计入“今日应到”。
- 取消、换单和运单更正保留历史。取消未收件可移出有效待收范围，但不得删除实收证据或掩盖已有异常。
- 保存成功时间、失败原因、处理数量与同步日志，支持手动补拉。

客户接口、授权方式、字段映射、分页方式与状态含义，需用实际系统验证；目前不宣称 BLUETTI 已有可直接使用的预报接口。

## 三、承运商记录池

优先验证 FedEx、USPS 能否提供独立来件记录。不能默认按仓库地址就能拉到完整清单，也不能默认客户自行购买的面单一定关联仓库账号。

| 接入方式 | 用途与边界 |
| --- | --- |
| 来件清单、账号级记录或事件订阅 | 有机会发现客户未预报的包裹；需验证权限、账号/仓库关联、覆盖范围、历史补拉和费用 |
| 按预报运单定时查询轨迹 | 独立清单不可用时的降级路径；可更新已知包裹，无法发现未知运单 |

两种方式的数据都进入承运商记录池，标明获取方式和覆盖范围。保存承运商、运单号、运输事件时间、系统接收时间、状态，以及来源提供的目的地等信息；保留事件历史和最新状态。

只有承运商记录、没有客户预报的包裹，也要保留并显示为待归属。若仅能查询已知运单，看板明确显示“仅覆盖已知运单”，不能把无记录解释成没有来件。

系统按包裹状态定时更新，重点跟踪派送中和近期送达未实收包裹；闭环包裹按策略降低频率或停止查询。频率、并发、重试与额度控制由管理员配置。失败或限流时保留成功数据并标记过期。

采用推送时需验证来源、去重并处理乱序和迟到事件，不能按最后接收时间直接覆盖业务状态；中断后按实际接口能力补查。

## 四、PDA 逐件实收

收货人员选择仓库与收货批次，扫描包裹运单上传 Web。先登记实际到仓，再关联客户工单，不要求先拆箱或查到 RMA 才能收货。

每次扫描记录唯一扫描 ID、原始条码、规范运单号、承运商、仓库、批次、人员、设备、设备扫描时间与服务器接收时间。人员身份必须可验证，不能仅凭共享设备密钥认定操作人。

- 有预报或运输记录时自动匹配，实时更新对账结果。
- 两池都无记录也允许实收，进入“未匹配实收”；预报晚到后重新匹配，无需重扫。
- 无法识别的条码保留原值进入待识别列表，不猜测归属。
- 离线暂存，联网补传；扫描 ID 保证上传幂等，同一包裹重复扫描保留事件但只计一件实收。
- 保留首次有效实收时间；误扫、错仓、撤销和更正需权限、原因与审计记录。
- 多来源匹配冲突交人工处理，不随意归到某客户。

## 五、对账与异常规则

以所属域/授权范围、承运商、规范运单号匹配，并核验目标仓库；客户和 RMA 是关联维度。设计时需考虑运单号重复使用的运输周期，避免长期运行后误合并旧包裹。

| 客户有效预报 | 承运商记录 | PDA 实收 | 结果 |
| --- | --- | --- | --- |
| 有 | 尚无有效状态 | 无 | 待运输数据/待核查，不能判定到货 |
| 有 | 正常运输中 | 无 | 待到货 |
| 有 | 今日预计到货或派送中 | 无 | 今日待收 |
| 任意 | 显示送达 | 无 | 送达待核实，超收货宽限时间后升级异常 |
| 有 | 任意或无记录 | 有 | 已实收；运输状态不同步时另列数据差异 |
| 无 | 有 | 无 | 承运商来件无预报，待归属 |
| 无 | 任意或无记录 | 有 | 未匹配实收，待补预报/归属 |
| 有 | 超预计日期且未送达 | 无 | 运输逾期，与送达未实收分开统计 |

“显示送达但未实收”是异常线索，不直接等于丢件。异常处理支持待核实、处理中、已解决、确认丢失，记录负责人、原因、证据与处理时间。客户同步失败、物流数据过期、PDA 离线积压单独提示，避免误报。

## 六、每日收货看板

默认当前仓库业务日，支持客户、承运商、仓库、日期和异常类型筛选，定时刷新。按仓库配置时区划分日期，不直接使用服务器或浏览器时区。

卡片包括：今日预计到货、今日派送中、今日承运商显示送达、今日实收、今日应到且已收、今日应到仍未收、超时送达未实收、未匹配实收、历史未闭环异常。

统计规则：

- 最新有效承运商预计日期优先，缺失时采用客户明确提供的预计日期，并标明来源。日期未知单列，不把全部未完工单算作今天应到。
- 派送中作为今日到货信号单列；送达按运输事件业务日统计，实收按首次有效扫描业务日统计。
- “今日实收”与“今日应到且已收”分别统计：今天扫到昨日包裹，不代表今天应到包裹已经收齐。
- 卡片维度可能重叠，不能直接相加为总件数；按包裹去重计数，工单数另列。
- 历史未解决差异不过午夜自动消失。保留收货结束时的差异快照，并关联后来补扫和处理结果。
- 离线补传保留扫描时间与上传时间，修正历史业务日归属时可追溯。
- 明细能展开关联工单、运输事件、扫描事件与异常处理记录。

顶部显示客户同步最后成功时间、承运商最后更新时间、PDA 上报情况、覆盖方式与未识别/冲突数量。数据不完整时不得仅因差异为零显示“全部收齐”。

支持结束本批收货并生成当时差异清单；结束批次不自动认定未收件丢失，也不阻止后续补收。

## 七、数据库与管理员配置

所有业务配置存数据库，在 Web 管理员界面维护，无需修改 XML：

| 类别 | 配置内容 |
| --- | --- |
| 客户系统 | 客户、来源连接、凭据、目标仓库、字段映射、工单范围、同步周期、首次回溯范围、启用开关 |
| 承运商 | 凭据、关联账号、测试/正式环境、接入方式、查询周期、并发、限流与重试 |
| 收货对账 | 仓库时区、送达收货宽限时间、运输逾期规则、批次规则 |
| 看板提醒 | 刷新周期、异常阈值、已获授权的提醒渠道和对象 |

保存后在约定的下一次调度或查询中生效，界面显示配置版本与生效情况。密钥加密存储且不回传明文，配置具备并发版本校验和变更审计。数据库连接沿用 Web 启动方式，加密根密钥仍需部署环境保管和备份。

区分配置管理、看板查看、PDA 实收、异常处理和纠错权限。收货人员无需管理员权限；按域、客户授权与仓库隔离数据。

## 八、服务与数据实体

Web 中设置客户同步任务、承运商同步任务、PDA 接收接口、对账服务和看板查询接口。两个同步任务独立运行；客户工单更新、运输状态变化、PDA 扫描到达均触发相关包裹重新对账。

建议实体：客户连接配置、承运商配置、来源工单、预报包裹、工单包裹关联、承运商事件、PDA 扫描事件、收货批次、异常处理单、同步游标与日志、配置/纠错审计。

工单、运输和扫描事实分别保存，对账结果可重算。任务需支持持久化游标、失败重试、手动补拉与多实例防重复执行。实际表结构在来源字段确认后设计，不以旧原型两张表作为完整方案。

## 九、实施顺序

1. 验证数据源：检查实际 BLUETTI 工单的运单字段、更新方式和接入权限；验证 FedEx/USPS 独立来件记录能力与覆盖范围。
2. 完成客户预报池：数据库配置、首次导入、定时增量同步、换单/取消处理与同步监控。
3. 完成承运商记录池：优先接独立记录，不可用则按预报运单自动查询并明确覆盖限制。
4. 接 PDA：在线/离线扫描、幂等上传、首次实收、未匹配登记、自动关联与纠错审计。
5. 完成每日看板、批次结束差异清单和异常闭环；提醒渠道确定并授权后再启用。
6. 选择客户和仓库小批试运行，人工对照实际到货检验两池覆盖率和看板准确性，再扩大范围。

## 十、验收标准

- 同一工单重复同步不增件；多包裹、换单、取消和迟到更新正确处理。
- 预报中的运单自动进入跟踪，不依赖逐单手工查询。
- 能独立获取的承运商来件在无客户预报时仍可见；能力受限时明确提示覆盖范围。
- 送达未扫先待核实，超宽限进入异常，补扫后闭环且保留历史。
- 无预报也可实收；预报晚到可匹配；重复扫描与离线重传不重复计件。
- 跨午夜、历史来件今日补扫、不同时区下，今日与历史差异统计正确。
- 同步失败、限流或设备离线时显示数据问题，不误报全部收齐。
- 普通收货人员可实收和看板查询，不能管理凭据；纠错可追溯。
- 修改凭据和同步周期按约定生效，无需修改 XML 或重启；任务重启可恢复进度。
