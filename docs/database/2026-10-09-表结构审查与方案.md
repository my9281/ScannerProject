# repairwms 表结构审查与解决方案

日期：2026-10-09。依据用户提供的结构快照及当前服务端、WPF、PDA 代码。范围为全部 11 张表与相关读写流程；未连接现场数据库，未执行修改，也未分析或归档表数据。因此“缺索引”等结构事实可确认；重复记录数量、数据是否污染及性能影响仍需现场检查。以下是本次可识别的问题，不承诺覆盖未知业务或全部运行时故障。

## 一、优先结论

优先解决：良品区 SN 唯一键缺失、上架请求缺少幂等标识、上架与新工单/扫码并发的一致性、SN 比较规则不一致，以及审核位状态含义。其次补索引、统一时间、记录操作来源，最后逐步整理历史表和维护策略。无需一次重建所有表。

目前已有的正确设计应保留：工单版本锁、账号外键、会话 token 哈希唯一、来源键去重、SKU/SN 批次 GUID 幂等、批次内 SN 唯一、上架与工单过滤/良品区删除同事务，以及库位禁用位不被重复上传覆盖。

优先级：P1 为可能直接造成重复或状态错误；P2 为维护、性能或边界风险；P3 为后续优化。它们是修复建议，不代表已在线修复。

## 三、重点方案与理由

### DB01：先修良品区去重

证据：结构快照 tester_pallet_scans 只有 uq_tester_pallet_scan_id；PalletScanRepository 使用 ON DUPLICATE KEY UPDATE，必须存在 SN 唯一才能按 SN 更新。此前主文档描述“SN 唯一”是目标/代码假设，当前现场快照并未具备，需要修正理解。

步骤：暂停扫描上传/上架写入 → 备份 → 决定 SN 比较规则 → 检查重复 → 按时间和 id 保留最新、归档其余 → 添加唯一键 → 测试同 SN 新 GUID 上传及跨设备并发。仓库 002 脚本会直接删除较旧记录，不能不经检查就部署。MySQL DDL 与清理不构成整体可回滚事务。

### DB02、DB03、DB24：请求幂等和当前状态

推荐分两步：先为上架增加固定请求 GUID，重试必须用同 GUID 和同内容，服务端验证内容哈希并返回原结果；再引入库存/设备当前状态和作业周期。上架明细仍保留历史，不能用 UNIQUE(sn) 代替请求幂等，否则合法再次维修上架会被拒绝。

所有扫码、工单生成和上架入口按同一资产/周期锁定状态行，校验“待检测 → 检测完成 → 已上架”等允许迁移。仅对三条 SQL 放事务不能防止事务之后另一接口创建新待办。已上架 SN 后续再扫是否允许，必须按新周期还是旧重试明确区分。

### DB05、DB27：完成与上架分离

继续保留 is_completed 和 audit_status 两列：平板保存仅修改检测完成；上架 API 修改上架标记，不能把完成等价为上架。现有 0/1 约定先固定，注释和界面消除“人工审核”歧义。补上架时间/来源后可追踪；若未来任务有其他审核状态，则新列比复用同一列更安全。

是否允许未完成工单直接上架、同 SN 多张工单如何匹配、返修如何重开，是业务决策，不凭表结构擅自阻止。

### DB04、DB09：编码和时间一致性

编码类型与语义分别定义：SN、SKU、托盘编号、库位 ID、用户名不必一律同排序规则。位置保留 VARCHAR(100)，不改 int；上架托盘字符串也保留。确认 SN 规则后进行碰撞预检，再迁移，不能一次 CONVERT 全库代替规则设计。

时间统一事件 UTC，业务日期单独定义；旧数据源混合时区时先按来源分类。连接固定 UTC，新写入统一；历史转换需明确原始来源和有效时区，无法判定的标注待核验。

## 五、执行顺序与验收

1. 运行只读检查，确认 SN 重复、排序规则、非法状态与批次计数；不删除数据。
2. 优先修复 DB01；上线固定上架 request_id，测试服务端成功但客户端超时的重试。
3. 增加工单 device_id 索引，核验上架/平板竞争：上架后旧版本保存应 409，刷新不再下发。
4. 明确再次扫码/返修周期，解决跨入口并发和旧事件覆盖，不靠追加唯一 SN 覆盖所有历史。
5. 逐步整理时间、状态、来源和描述字段，加入迁移版本及部署前检查。
6. EXPLAIN 与实际数据量决定其余索引和分页；最后整理历史 orders 与归档期限。

所有结构变更先在测试库验证，保留数据备份和回退方案；唯一键/字符集迁移失败时不跳过错误继续部署。无需现在执行全部建议，代码和 SQL 分阶段发布。

只读预检见 [检查 SQL](repairwms-review-checks.sql)；结构基线见 [数据库档案](README.md)。查询只输出聚合异常数量，不归档用户数据。建议的唯一键、删除和状态回填不包含在此检查脚本中。
